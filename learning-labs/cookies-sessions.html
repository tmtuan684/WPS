Why this matters

HTTP forgets everything. Your app can't afford to.

Every request a browser sends is, by default, a stranger walking up to the counter for the first time — no matter that they ordered two minutes ago. Cookies and sessions are the two mechanisms the web stack gives us to fix that: one keeps a small note in the customer's pocket, the other keeps a ledger behind the counter. This week you'll implement both — first in raw JavaScript, then in Express — and learn when to reach for each.

By the end of this reading you should be able to set, read, and delete cookies from both the browser and an Express server; stand up express-session to track a logged-in user; and explain, in a sentence, why session IDs live in a cookie but passwords never should.

Client-side · the loyalty card

What is a cookie?

A cookie is a small text file (≤ ~4 KB) that the browser stores on the customer's own device and hands back to your server on every subsequent request to the same domain — like a loyalty card the customer keeps in their wallet and shows at every visit.

Server sets the cookie

Saigon Sips' server sends a Set-Cookie header after your first order — e.g. a customer ID.

Browser stores it

Chrome files the cookie away and decides, based on its attributes, when and where to resend it.

Browser resends it

On every later request to saigonsips.com, the browser attaches the cookie via the Cookie header — no extra work from your code.

Types & attributes worth knowing

Type / AttributeWhat it means
Session cookieNo expiry set — vanishes when the browser closes. Good for "remember my cart while I shop today."
Persistent cookieHas an expiry date — survives restarts. Good for "remember my name for next month."
HttpOnlyHidden from document.cookie / JavaScript. Blocks a whole class of XSS cookie-theft attacks.
SecureOnly ever sent over HTTPS — never sniffable on plain HTTP.
SameSiteControls whether the cookie rides along with cross-site requests. Strict or Lax is your CSRF defence.
Rule of thumb
A cookie is visible and editable by whoever holds the browser. Store an identifier in it (a customer ID, a cart token) — never a password, a balance, or anything that would be dangerous if the customer simply edited the text file themselves.
Implementation

Working with cookies

Create a cookie

// path "/" means the cookie is valid across the whole site
document.cookie = "member=Mai Tran; expires=Thu, 18 Dec 2028 12:00:00 UTC; path=/";

Read & parse a cookie

document.cookie returns every cookie as one semicolon-joined string, so reading a single value means parsing it yourself:

function getCookieValue(name) {
  const nameEQ = name + "=";
  const parts = document.cookie.split(';');
  for (let part of parts) {
    part = part.trim();
    if (part.indexOf(nameEQ) === 0) {
      return part.substring(nameEQ.length);
    }
  }
  return null;
}

console.log(getCookieValue('member')); // "Mai Tran"

Delete a cookie

There's no document.deleteCookie() — you delete a cookie by re-setting it with a date in the past:

document.cookie = "member=; expires=Thu, 01 Jan 1970 00:00:00 UTC; path=/";
Inspect it yourself
DevTools → Application tab → Storage → Cookies → your site. The Cookie-Editor Chrome extension is handy for quickly toggling HttpOnly, Secure, and Session on any cookie while you experiment.

Set a cookie from the server

const express = require('express');
const app = express();

app.get('/order', (req, res) => {
  res.cookie('member', 'Mai Tran', { maxAge: 900000, httpOnly: true });
  res.send('Welcome back — cookie set for 15 minutes.');
});

app.listen(3000, () => console.log('Saigon Sips running on port 3000'));

maxAge is in milliseconds (900000 ms = 15 min). Set httpOnly: true by default — only turn it off if client-side JS genuinely needs to read that value.

Read a cookie

Express doesn't parse incoming cookies on its own — install the cookie-parser middleware first:

npm install cookie-parser
const cookieParser = require('cookie-parser');
app.use(cookieParser());

app.get('/whoami', (req, res) => {
  const member = req.cookies.member;
  res.send(member ? `Welcome back, ${member}!` : 'New customer — no cookie yet.');
});

Delete a cookie

app.get('/logout', (req, res) => {
  res.clearCookie('member');
  res.send('You have been logged out.');
});
Server-side · the back-office ledger

What is a session?

A session keeps the actual data on the server — in memory, in Redis, in a database — and gives the client only a ticket number to prove which ledger entry is theirs. That ticket number is itself delivered and returned using... a cookie. Sessions and cookies aren't rivals; sessions use a cookie as their pointer.

Session ID created

You log in; the server opens a fresh entry in its ledger and mints a unique session ID for it.

ID sent to client

That ID is stored in a cookie — typically named connect.sid — nothing else about you leaves the server.

Server looks it up

Each later request carries the cookie back; the server uses the ID to fetch your row from its ledger.

Because the sensitive data (user ID, login status, cart contents) never leaves the server, sessions are the safer home for anything you wouldn't want a customer editing themselves.

Implementation

Setting up express-session

Install & configure

npm install express express-session ejs
const session = require('express-session');

app.use(session({
  secret: 'yourSecretKey',   // signs the session-ID cookie — keep this out of source control
  resave: false,             // don't re-save a session that wasn't modified
  saveUninitialized: false,  // don't set a cookie before the user actually needs one (GDPR-friendly)
  cookie: { secure: false, maxAge: 60000 } // secure:true once you're on HTTPS
}));

Store data on login

app.post('/login', (req, res) => {
  // assume the credentials have already been verified against MongoDB
  const user = { _id: 1, name: 'Mai Tran' };
  req.session.userId = user._id;
  req.session.isLoggedIn = true;
  res.redirect('/dashboard');
});

Read it back on a protected route

app.get('/dashboard', (req, res) => {
  if (req.session.isLoggedIn) {
    res.render('dashboard', { userId: req.session.userId });
  } else {
    res.redirect('/login');
  }
});

Destroy the session on logout

app.get('/logout', (req, res) => {
  req.session.destroy((err) => {
    if (err) return res.redirect('/dashboard');
    res.clearCookie('connect.sid');
    res.redirect('/login');
  });
});
Try this before class
Log in to your local demo, open DevTools → Application → Cookies, and manually delete connect.sid. Reload /dashboard. What happens — and why does deleting one small cookie undo an entire login, even though the session data is still sitting on the server?
Note
This demo is intentionally minimal — a hardcoded user object, no password check, no database. Assignment 4 asks you to wire this same pattern up to real MongoDB-backed authentication.

Cookies vs. Sessions

🍪 Cookies

  • Live in the browser, on the customer's device
  • Can persist for years if you choose
  • Readable/editable by the client — never trust them blindly
  • Good for: preferences, "remember me" tokens, analytics IDs

🗄️ Sessions

  • Live on the server; client only holds a pointer (in a cookie)
  • Usually short-lived — closes with the browser or a timeout
  • Safer, since real data never reaches the client
  • Good for: login state, shopping cart contents, anything sensitive
FeatureCookiesSessions
Storage locationClient's browserServer, referenced by a client-side ID
LifespanSet by expires/maxAge, can be permanentTypically ends with the browser session or a server timeout
SecurityVulnerable if not flagged Secure/HttpOnlySafer — only the ID is exposed, not the data
Don't skip this

Security checklist

SecureOnly send cookies over HTTPS — non-negotiable in production.
HttpOnlyBlock JS access to sensitive cookies, closing off a common XSS path.
SameSiteUse Strict or Lax to blunt CSRF attacks.
RegenerateIssue a fresh session ID on login to defeat session-fixation attacks.
ExpireShort session timeouts limit the damage of a stolen session ID.
Never storePasswords, card numbers, or anything sensitive directly in a cookie.
