Node.js Lab · Foundations Track

From Browser to Backend

You already know JavaScript — the syntax, the functions, the async patterns. Node.js runs on the exact same engine as your browser. This lab is about the part that's actually new: what disappears (the DOM), what shows up in its place (the operating system), and how the async style you already know from fetch() carries straight over to reading files and talking to the outside world.

Level 01 · Beginner

Foundations

Same language, missing pieces, new pieces. Before writing anything clever, get comfortable with what Node actually is and what it hands you instead of the DOM.

What Node Actually Is

Node.js is not a new language — it's the same V8 engine that runs JavaScript inside Chrome, unplugged from the browser and given access to the operating system instead. That single fact explains almost everything that surprises people at first: the syntax you know still works exactly the same; what changes is which objects exist in the global scope.

In the browser (what you know) 
console.log(window.innerWidth);
document.querySelector('h1');
localStorage.setItem('x', '1');
In Node.js (what's new) 
console.log(process.platform);
// document is undefined — no DOM in Node
// localStorage doesn't exist — use fs instead

window and document throw ReferenceError in Node — they're browser-only objects, not part of JavaScript itself. In exchange, Node gives you process, and a set of built-in modules (fs, path, http, and more) for talking to files, the network, and the OS — things a browser deliberately keeps a web page away from, for your computer's safety.

The REPL — Your Node Console

Typing node with no filename drops you into the REPL (Read-Eval-Print Loop) — think of it as DevTools' console tab, minus the DOM, plus a few Node-only globals to explore.

terminal 
$ node
> 2 + 2
4
> const greet = name => `Hi, ${name}!`;
undefined
> greet('Tuan')
'Hi, Tuan!'
> window
Uncaught ReferenceError: window is not defined
> .exit

process & argv

process is a global object Node hands you automatically — no require needed. process.argv is an array of the command-line arguments the script was launched with; the first two entries are always the path to Node itself and the path to your script, so your actual arguments start at index 2.

greet.js 
// process.argv[0] = path to node
// process.argv[1] = path to this file
// process.argv[2] onward = your arguments
const name = process.argv[2] || 'stranger';
console.log(`Hello, ${name}!`);
node greet.js Tuan
Exercise 1.1

Personalized Greeter with a Twist

Extend greet.js so it accepts two arguments: a name and a time of day (morning, afternoon, or evening). Print a matching greeting. If the time-of-day argument is missing or doesn't match one of the three, default to a generic "Hello".

Hint

Read process.argv[2] and process.argv[3] into two variables. A switch statement (or an object lookup keyed by the time-of-day string) works well for picking the right greeting word.

Solution
greet.js 
const name = process.argv[2] || 'stranger';
const timeOfDay = process.argv[3];

const greetings = {
  morning: 'Good morning',
  afternoon: 'Good afternoon',
  evening: 'Good evening'
};

const greeting = greetings[timeOfDay] || 'Hello';
console.log(`${greeting}, ${name}!`);
node greet.js Tuan evening
Level 02 · Beginner–Intermediate

Modules & Files

Splitting code into files is something you already do with import/ export in modern frontend tooling. Node has its own long-standing version of that idea — plus something the browser never gives you: real file system access.

Two Module Systems

If you've used a bundler like Vite or webpack, import/ export already feels familiar — that's ES Modules (ESM), and modern Node supports it directly. But most existing Node code — tutorials, older packages, the whole npm ecosystem's history — uses Node's original system: CommonJS, with require and module.exports. You'll meet both, so it's worth recognizing them as two spellings of the same idea.

ES Modules (what you already know) 
// math-utils.js
export function add(a, b) {
  return a + b;
}

// app.js
import { add } from './math-utils.js';
CommonJS (Node's traditional way) 
// math-utils.js
function add(a, b) {
  return a + b;
}
module.exports = { add };

// app.js
const { add } = require('./math-utils.js');

To use ES Modules in Node, save files with a .mjs extension, or add "type": "module" to package.json. Otherwise Node assumes CommonJS by default. Each module also gets its own private scope automatically — variables in math-utils.js don't leak into app.js unless explicitly exported, which is part of why splitting code into modules keeps it organized.

Requiring a Directory

require() can load an entire folder as one module — Node looks for an index.js inside it by default. This is handy for grouping related files behind one clean import path.

utils/index.js 
module.exports = {
  ...require('./math-utils.js'),
  ...require('./string-utils.js')
};
app.js 
// loads utils/index.js automatically
const { add, capitalize } = require('./utils');

The fs Module — Access You Never Had Before

Browsers deliberately block JavaScript from touching your file system — imagine if any website could read your documents. Node has no such sandbox: it's meant to run trusted code on servers and your own machine, so the built-in fs module gives full read/write access. That's genuinely new territory, not just a renamed browser API.

fs-basics.js 
const fs = require('fs');

// Sync — blocks execution until done, simplest to read top-to-bottom
fs.writeFileSync('greeting.txt', 'Hello from Node!');
const content = fs.readFileSync('greeting.txt', 'utf8');
console.log(content);

// mkdirSync creates a folder; the { recursive: true } option
// avoids an error if it already exists
fs.mkdirSync('logs', { recursive: true });
Exercise 2.1

A Tiny Notes Module

Create a module notes.js that exports two functions: addNote(text), which appends a note to a notes.json file (creating it if it doesn't exist yet, starting from an empty array), and readNotes(), which returns the full array of saved notes. Then write a small app.js that requires the module and adds a note passed in via process.argv.

Hint

Use fs.existsSync() to check whether notes.json exists before reading it. Read the current array with JSON.parse(fs.readFileSync(...)), push the new note, then write it back with fs.writeFileSync(..., JSON.stringify(notes, null, 2)).

Solution
notes.js 
const fs = require('fs');
const FILE = 'notes.json';

function readNotes() {
  if (!fs.existsSync(FILE)) return [];
  return JSON.parse(fs.readFileSync(FILE, 'utf8'));
}

function addNote(text) {
  const notes = readNotes();
  notes.push({ text, createdAt: new Date().toISOString() });
  fs.writeFileSync(FILE, JSON.stringify(notes, null, 2));
}

module.exports = { addNote, readNotes };
app.js 
const { addNote, readNotes } = require('./notes.js');

const noteText = process.argv.slice(2).join(' ');
if (noteText) addNote(noteText);

console.log(readNotes());
node app.js Buy more coffee for the office
Level 03 · Intermediate

Async Node

This is where prior JavaScript knowledge pays off the most: the Promise/async-await mental model you already have from fetch() maps directly onto Node's I/O. Same shape, different job underneath.

Why This Feels Familiar

In the browser, fetch() doesn't freeze the page while a network request is in flight — it returns a Promise, and your code moves on. Node applies the exact same idea to file reads, network calls, and timers: operations that would otherwise sit and wait are handed off, and Node moves on to start the next thing immediately.

Browser — non-blocking network 
const res = await fetch('/api/data');
const data = await res.json();
Node — non-blocking file read 
const fs = require('fs').promises;
const data = await fs.readFile('data.json', 'utf8');

Callbacks, and Why They Get Messy

Node's oldest I/O functions (like fs.readFile, not fs.readFileSync) use plain callbacks: a function you pass in that gets called once the operation finishes. Read three files back to back and you get nested callbacks — "callback hell."

callback-hell.js 
const fs = require('fs');

fs.readFile('file1.txt', 'utf8', (err, data1) => {
  if (err) throw err;
  fs.readFile('file2.txt', 'utf8', (err, data2) => {
    if (err) throw err;
    fs.readFile('file3.txt', 'utf8', (err, data3) => {
      if (err) throw err;
      console.log('All three files read.');
    });
  });
});

Each level of nesting adds its own error handling, and the "pyramid" shape gets harder to read and modify the deeper it goes.

Flattening It: Promises, Then Async/Await

Node's fs.promises gives you Promise-returning versions of the same functions. Chain them with .then(), or — cleanest of all — use async/await, exactly like you would with fetch() in the browser.

async-await.js 
const fs = require('fs').promises;

async function readAllFiles() {
  try {
    const data1 = await fs.readFile('file1.txt', 'utf8');
    const data2 = await fs.readFile('file2.txt', 'utf8');
    const data3 = await fs.readFile('file3.txt', 'utf8');
    console.log('All three files read.');
  } catch (err) {
    console.error('Something failed:', err);
  }
}

readAllFiles();

One try/catch now covers every step — a direct improvement over checking err at every nesting level by hand.

Exercise 3.1

Refactor & Time It

Starting from the nested-callback version above, refactor readAllFiles into an async function using fs.promises and await. Then wrap the calls with console.time('read') / console.timeEnd('read') to measure how long all three reads took together.

Hint

console.time(label) starts a timer; calling console.timeEnd(label) with the same label later prints the elapsed time. Place the two calls around your await chain, inside the try block.

Solution
timed-read.js 
const fs = require('fs').promises;

async function readAllFiles() {
  console.time('read');
  try {
    const data1 = await fs.readFile('file1.txt', 'utf8');
    const data2 = await fs.readFile('file2.txt', 'utf8');
    const data3 = await fs.readFile('file3.txt', 'utf8');
    console.log('All three files read.');
  } catch (err) {
    console.error('Something failed:', err);
  } finally {
    console.timeEnd('read');
  }
}

readAllFiles();

Bonus to try afterward: swapping the three sequential await calls for Promise.all([...]) reads all three files concurrently instead of one after another — worth comparing the timer output between both versions to see the difference directly.

Level 04 · Capstone

Capstone Build: Superhero Joke CLI

A small command-line app that pulls together everything so far: npm packages, process.argv, fs, and async/await — the same four ideas from Levels 1–3, combined into one real tool.

Setting Up

Start a fresh project and install three small npm packages: one for jokes, one for superhero names, and one for colored terminal output.

terminal 
$ npm init -y
$ npm install give-me-a-joke superheroes chalk

The App

This version wires the packages together with what you already know: an async function to await the joke, process.argv to accept an optional --save flag, and fs.promises to append the result to a log file when that flag is present.

superhero-joke.js 
const chalk = require('chalk');
const superheroes = require('superheroes');
const jokeGenerator = require('give-me-a-joke');
const fs = require('fs').promises;

// give-me-a-joke's API is callback-based, so we wrap it in a
// Promise once, and get to use await everywhere else in the app
function getRandomJoke() {
  return new Promise((resolve) => {
    jokeGenerator.getRandomDadJoke((joke) => resolve(joke));
  });
}

async function main() {
  const shouldSave = process.argv.includes('--save');
  const hero = superheroes.random();
  const joke = await getRandomJoke();

  const output = `${chalk.bold.green(hero)} says:\n${chalk.yellow(joke)}`;
  console.log(output);

  if (shouldSave) {
    const logLine = `[${new Date().toISOString()}] ${hero}: ${joke}\n`;
    await fs.appendFile('joke-log.txt', logLine);
    console.log(chalk.dim('Saved to joke-log.txt'));
  }
}

main();
node superhero-joke.js --save

Extend It Yourself

Take the app above and work through this checklist. Each item reuses a concept from an earlier level — this is the point where the pieces stop being separate exercises and start being one toolkit.

  • Add a --count N flag that prints N jokes in a row instead of just one (Level 1: process.argv parsing).
  • Wrap the whole main() body in try/catch so a failed joke fetch doesn't crash the process with an unhandled rejection (Level 3: async error handling).
  • Add a --history flag that, instead of fetching a new joke, reads and prints every line already saved in joke-log.txt (Level 2: fs reads).
  • Split the joke-fetching and file-logging logic out into their own joke-service.js module, and require it from the main file (Level 2: modules).
Exercise 4.1

Implement --count and --history

Try the first and third checklist items yourself before checking the solution.

Solution
superhero-joke.js (extended) 
async function main() {
  const shouldSave = process.argv.includes('--save');
  const showHistory = process.argv.includes('--history');

  if (showHistory) {
    try {
      const log = await fs.readFile('joke-log.txt', 'utf8');
      console.log(log);
    } catch {
      console.log(chalk.dim('No history yet — run without --history first.'));
    }
    return;
  }

  const countFlagIndex = process.argv.indexOf('--count');
  const count = countFlagIndex !== -1
    ? parseInt(process.argv[countFlagIndex + 1], 10) || 1
    : 1;

  for (let i = 0; i < count; i++) {
    const hero = superheroes.random();
    const joke = await getRandomJoke();
    console.log(`${chalk.bold.green(hero)} says:\n${chalk.yellow(joke)}\n`);

    if (shouldSave) {
      const logLine = `[${new Date().toISOString()}] ${hero}: ${joke}\n`;
      await fs.appendFile('joke-log.txt', logLine);
    }
  }
}

Where this goes next

Everything above runs on your own machine, triggered from a terminal. The next step is Express — which takes this same Node runtime and uses it to listen for HTTP requests instead of command-line arguments, so a "request" becomes your new entry point instead of process.argv. EJS then handles turning data into HTML on the server, the way your frontend code already turns data into DOM updates in the browser. Same engine, same async instincts — just a different trigger for your code to run.
