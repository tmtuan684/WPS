00 · Orientation

One thread, two ways to wait

Node.js runs your JavaScript on a single thread. When that thread is busy, nothing else can happen — no other request, no timer, no I/O callback. The entire question of "sync vs async" comes down to one thing: does an operation give the thread back while it waits, or does it hold onto it?

Synchronous

const data = fs.readFileSync(path);
// thread is stuck here until
// the read completes — nothing
// else can run in the meantime
console.log(data);

Asynchronous

fs.readFile(path, (err, data) => {
  console.log(data);
});
// thread moves on immediately —
// the callback fires later, once
// the read finishes in the background
How to use this lab Sections 01–03 all read the exact same simulated file, with the exact same simulated disk latency (~2.2s) — only the method changes. Keep an eye on the heartbeat counter in the sidebar each time you click Run. It's the whole lesson.
Teaching note In Node, a blocked thread freezes the entire server — every connected client, not just one browser tab. This lab can only freeze itself (one page), but it's the identical mechanism: JavaScript is single-threaded both in the browser and in Node.

You might not see the first line appear right away Since the thread is fully blocked — including rendering — the browser may not even paint "About to call fs.readFileSync..." to the screen until after the whole 2.2s freeze ends. Everything can appear to show up at once. That's not a bug in this lab; it's the same reason a real blocked Node server can't even flush a "still working..." log line to a client until it unblocks.

04 · Watch it run

Why this matters more with multiple requests

Imagine a tiny server where 3 clients each request a file read, arriving at almost the same moment. Run both modes below and compare the total time and the pattern of completion.

If the server uses readFileSync

app.get('/file', (req, res) => {
  // blocks ALL other clients
  // until this one's read finishes
  const data = fs.readFileSync(path);
  res.send(data);
});

If the server uses fs.promises

app.get('/file', async (req, res) => {
  // other clients keep being served
  // while this read is in progress
  const data = await fsPromises.readFile(path);
  res.send(data);
});
Client A (900ms)
Client B (1300ms)
Client C (700ms)
Ready.
What to look for In "Sync" mode, the bars run strictly one after another — Client B's bar doesn't even start until Client A's finishes, and total time is the sum of all three. In "Async" mode, all three bars start together and run concurrently, so total time is roughly the slowest single request, not the sum.
05 · Practice deciding

When to actually use each

Sync isn't "wrong" — it's wrong in the wrong context. For each scenario below, decide: would you reach for a Sync method or an async one (callback/promises)?

Cheat sheet

Use Sync when…Use Async when…
It's a one-off CLI tool or build script that runs top-to-bottom and exits Code runs inside a web server handling multiple requests/users
You're at startup/module-load time, before anything else depends on responsiveness (e.g. reading a config file once when the process boots) Anything that could run concurrently with other work — HTTP handlers, WebSocket events, background jobs sharing the process
Strict ordering matters and blocking is actually the simplest correct way to express "do this, then that" (e.g. simple migration/setup scripts) You care about throughput or responsiveness under load — even a single slow sync call can stall every other client
The file is small and the operation is genuinely quick, so blocking is momentary and low-risk The file could be large, remote, or slow (network-mounted disks, big uploads) — sync risk scales with how long the block lasts
